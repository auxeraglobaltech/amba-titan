What titan-axi is

titan-axi is the complete OpenTitan Earl Grey chip — a security microcontroller with an Ibex RISC-V core and about 50 peripheral and security IPs — in which the two on-chip crossbars have been replaced by an AXI4 fabric.

The IPs themselves are untouched OpenTitan RTL. Their register ports speak TileLink-UL (TL-UL), so a small bridge sits directly in front of every IP. Between modules, every transaction is AXI.

Around the chip is a fresh UVM testbench, and C firmware runs on the real CPU from a hex image loaded into ROM.

Think of the chip as a city whose districts (IPs) all speak an old local language (TL-UL). The new highway system between districts (the AXI fabric) uses a modern standard. At every district's gate there is an interpreter (a bridge). Traffic on the highways is all AXI; inside each district it is still TL-UL.

Which statement about the IPs in titan-axi is true?

The IPs keep their reggen-generated TL-UL register blocks. titan_axi2tlul sits right in front of each, so AXI runs everywhere between modules: CPU → crossbar → crossbar → IP bridge.

Good & bad practices

✓ Good practice

Refer to ports by their testbench port name (dev.uart0) in bug reports and test plans, and give the hierarchy path alongside.

Why: the port name is what the scoreboard, the tracer and the generated address map all use; the path lets a designer jump straight to it.

✗ Common mistake

Editing generated files (titan_axi_fabric.sv, titan_axi_probe.sv, titan_addr_map_pkg.sv, regs/*.h) by hand.

Why it hurts: the next regeneration silently undoes your change, and worse, the testbench's address map can drift from the RTL's.

✓ Good practice

Keep test content in firmware/ and uvm/ only.

Why: rtl/ is the DUT. A testbench that needs the DUT changed to pass is not testing the DUT.

✗ Common mistake

Reading the probe signals as if they were extra design logic.

Why it hurts: the probe only mirrors fabric wires. The one exception is P.if_host_sim_host, which the testbench drives (stub-CPU tests).

Good & bad practices

✓ Good practice

Before debugging a hang, find which clock domain the target IP is in.

Why: a transaction to the peripheral side spends most of its latency in the 24 MHz domain and the CDC; "slow" there is normal, a hang is not.

✗ Common mistake

Assuming the CPU can execute code from any memory.

Why it hurts: the instruction port only reaches 4 devices. Code copied to retention SRAM faults on the first fetch — by design.

✓ Good practice

Use the UVM master (stub-CPU tests) to bring up a new path before writing firmware for it.

Why: one AXI read from the testbench isolates fabric problems from software problems.

✗ Common mistake

Gating a peripheral clock and then touching that peripheral.

Why it hurts: the device bridge waits forever for a TL-UL response from a stopped IP, and the bus behind it hangs.

Host bridge — titan_tlul2axi

Turns a TL-UL initiator (Ibex, rv_dm) into an AXI master. Three rules make a one-channel, in-order protocol safe on five channels:

  1. One AXI ID per port (always 0). AXI only keeps responses in order within one ID, and Ibex's TL-UL adapter cannot reorder.
  2. No read/write mixing in flight. AR and AW are independent, so "store X, then load X" could swap. A request in the other direction waits until the outstanding ones have returned.
  3. Integrity is carried, not regenerated. The TL-UL ECC rides in USER bits. Only when no device answered (DECERR, USER all zero) does the bridge build the response integrity itself — otherwise Ibex would raise a fatal integrity alert instead of a clean access fault.
// titan_tlul2axi.sv — rule 2: a new request may enter only if it goes the same
// direction as everything still outstanding (or nothing is outstanding).
assign dir_ok  = ~pend_rvalid | (dir_is_wr_q == a_is_wr);
assign a_ready = (~hold_q | hold_done) & pend_wready & dir_ok;

Device bridge — titan_axi2tlul

  • AR and AW are served one command at a time, round-robin.
  • Bursts are split: one TL-UL request per AXI beat (INCR, FIXED, WRAP).
  • Integrity passes through for single-beat transactions that came from a TL-UL host (AxUSER.intg_vld = 1); otherwise (UVM master, bursts) the bridge generates it.
  • Answered SLVERR without touching the IP: ATOPs, beats wider than 32 bits, reserved burst types, illegal WRAP lengths.

Activity — predict the device-side ID

In axi_csr_reset the UVM sequence issues reads with ID 0. What arid do you expect at P.if_dev_uart0? And for a CPU instruction fetch at P.if_dev_rom_ctrl_rom?

xbar_main prepends the 2-bit index of the slave port the transaction came in on. xbar_peri has only one slave port, so it adds nothing.
UVM master = index 3: {2'd3, 4'd0} = 6'h30 at dev.uart0 (also 6'h30 on link.main_to_peri). Fetch = index 0, bridge ID 0: 6'h00.

Why does titan_tlul2axi hold a read back while a write is still outstanding?

The bridge testbench (uvm/bridge_tb, check C2) issues store-then-load pairs back to back to prove this rule.

A CPU load hits an unmapped address. What reaches Ibex?

The crossbar's error slave answers DECERR with USER = 0. The host bridge sees intg_vld = 0 and generates the integrity itself (rule 3), matching what OpenTitan's own tlul_err_resp would return.

Good & bad practices

✓ Good practice

When a transaction looks wrong at the IP, compare its ID at the device port: the top two bits tell you who sent it.

Why: with four initiators, "who issued this?" is the first question, and the ID answers it without tracing back.

✗ Common mistake

Writing a UVM sequence that sends an atomic (ATOP) and expecting the IP to see it.

Why it hurts: u_sim_host_atop_filter answers it with SLVERR before the crossbar. The scoreboard will report a host transaction that never reached a device.

✓ Good practice

Prove bridge changes in uvm/bridge_tb first (seconds per run), then at chip level.

Why: a broken bridge makes every chip test fail at once, far from the cause.

✗ Common mistake

Expecting an AXI burst to reach a TL-UL IP as a burst.

Why it hurts: TL-UL has no bursts; the device bridge issues one request per beat. Look for N TL-UL requests, not one.

Address decode in one paragraph

u_xbar_main decodes every address against its 27 rules (the peri device owns two windows; rv_core_ibex.cfg owns two pieces around the simulation window). A hit on peri goes through u_cdc_peri to u_xbar_peri, which decodes against its own 27 rules. A miss at either crossbar is answered DECERR by that crossbar. So a miss inside the peripheral windows still crosses the CDC first — useful when you read waves.

For each address say which port answers, or which crossbar gives DECERR: (a) 0x4001_0040, (b) 0x4101_0000, (c) 0x4060_0FFC, (d) 0x411F_0084.

uart1's window is 64 bytes. Check whether each address falls inside one of xbar_main's two peri windows first.
(a) inside the peri window but past uart1's 64-byte window → DECERR from xbar_peri (crosses the CDC first). (b) gap between flash_ctrl.prim and aes → DECERR from xbar_main. (c) last word of retention SRAM → dev.sram_ctrl_ret_aon.ram. (d) dev.titan_sim_ctrl, the LOG register (simulation builds only).

The firmware's stack lives at the top of a 16 KiB region starting near 0x1000_0000. Which memory is that, and which crossbar serves it?

link/rom.ld puts .data, .bss and a 16 KiB stack in main SRAM at 0x1000_0000. The stub-CPU tests use 0x1001_0000 and up so they never touch it.

Good & bad practices

✓ Good practice

Take addresses from firmware/include/top_earlgrey.h (C) or titan_addr_map_pkg (SV) — never type them twice.

Why: both are generated from the same source as the RTL; hand-typed copies drift.

✗ Common mistake

Treating SLVERR and DECERR as the same thing.

Why it hurts: SLVERR means a device answered and refused (e.g. an unimplemented register); DECERR means no device exists there. They point to completely different bugs.

What crt0.S does before main() — and why

#StepWhy it is needed on Earl Grey
1Open the PMP: one locked all-access rule (entry 15), reset rules clearedThe reset PMP uses MMWP: M-mode may only touch what a rule allows, and the reset rules allow only the first 2 KiB of ROM, MMIO and the debug ROM — not main SRAM (the stack) or the PLIC. So this must run from the first 2 KiB of ROM; rom.ld asserts it does.
2Calibrate the clocks: rewrite AST REGAL, wait for AST_INIT_DONEThe oscillators start uncalibrated (IO clock ~26 MHz instead of 96). Without this every baud rate and microsecond is ~4× off — this broke the UART test on first bring-up.
3Initialize main SRAM (sram_ctrl CTRL.INIT)Until written, SRAM words have bad ECC; reading one is an integrity error.
4Zero .bss, copy .data, write IN_TEST, call main(), write PASSED/FAILEDThe usual C runtime start, plus the report to the testbench.

Activity — why did it not boot?

A trainee moves a large lookup table into crt0.S's .crt section, before the PMP code. The link fails with crt0 must fit in the first 2 KiB of ROM. Why does this rule exist, and what should they do?

Which addresses may the CPU fetch from before step 1 has run?
Until the PMP is opened, the reset rule allows execution only from 0x8000–0x87FF. Code beyond that faults before it can open the PMP. Put the table in .rodata (any C const array): only the boot code must be in the first 2 KiB.

Your UART test receives garbage, but the timer test passes. What is the most likely cause?

Exactly what happened on the first regression run. A firmware-only check (timer) is self-consistent with a wrong clock; a testbench check against absolute time (UART at 1 Mbaud, clk_freq) is not.

Good & bad practices

✓ Good practice

Check pins and timing from the testbench side too, not only in C.

Why: firmware that measures time with a wrong clock agrees with itself. Only an external observer catches it.

✗ Common mistake

Reading a peripheral input pin that nothing drives.

Why it hurts: an undriven pad reads X, and X on the bus trips assertions microseconds later, far from the cause. The testbench pulls every pad; keep it that way.

✓ Good practice

Use titan_sync(n) whenever the testbench must act at a precise point in the firmware.

Why: it replaces fragile fixed delays with an explicit handshake you can see in the log.

✗ Common mistake

Keeping a constant (pattern table, message) in the C file and a copy in the UVM test without saying so.

Why it hurts: nothing links them at compile time; change one and the test fails for no visible reason. Comment both sides.

Activity — what would the scoreboard say?

A bug in the fabric generator swaps the address rules of uart0 and uart1. A test reads 0x4000_0014. Which component reports what?

The scoreboard decodes with the generated map, then looks for the twin in that device's queue.
fabric_scoreboard: "never seen at dev.uart0" for the host read, and at the end "device transaction with no host twin" for the read that actually arrived at dev.uart1. This works because the scoreboard does not read the RTL's rules: its map (titan_addr_map_pkg) is generated from fabric_ports.json, a separate output. A mistake in emitting the SV rules shows up as a disagreement between the two.

Which probe interface is not read-only?

Only the stub-CPU master port is driven. When no test uses it, the driver keeps all VALIDs low, so the fabric sees an idle fourth host.

Good & bad practices

✓ Good practice

Let the scoreboard do interconnect checking for free in every test; write test-specific checks only for what the test is about.

Why: ~20k transactions per test are checked without a line of test code.

✗ Common mistake

Driving a probe interface from a test to "help" the design.

Why it hurts: the probe mirrors the design with continuous assignments; a second driver creates X or hides the real behaviour.

✓ Good practice

Get virtual interfaces from uvm_config_db by port name, as the env does.

Why: tests never contain hierarchy paths, so they survive changes in the fabric's structure.

✗ Common mistake

Sampling DUT signals on the clock edge in procedural code without a clocking block.

Why it hurts: race conditions. The bridge testbench's first run failed 397 checks because one task sampled a ready signal before its own request had been driven.

You want to prove that writing CLK_ENABLES stops clk_io_peri. Which kind of test is it, and which existing test is the model?

Who writes the register, and who can see a clock stop?
C + UVM: firmware writes the register and calls titan_sync(); the UVM test counts clock edges with env.clk.count_edges(). It already exists: fw_clk_gate (firmware/tests/clk_gate.c + fw_clk_gate_test).

Good & bad practices

✓ Good practice

Run the slang lint before a long build after any SV change.

Why: it finds syntax, type and port errors in about a minute without a licence; it caught a reserved-word variable name and a clocking-block conflict before they reached Xcelium.

✗ Common mistake

Running several simulations at once on the shared server.

Why it hurts: they share runs/build and the licence pool; runs slow down or corrupt each other's snapshot.

✓ Good practice

Add a test to tests.list only once it passes, and record the seed of every failure.

Why: the regression stays a meaningful green/red signal, and failures stay reproducible.

✗ Common mistake

Trusting a log without checking its timestamp.

Why it hurts: a failed build leaves the previous run's log in place — it looks like a fresh pass.

A UVM burst of 4 beats to main SRAM. How many TL-UL a_valid handshakes appear on F.tl_sram_ctrl_main__ram_o?

The device bridge issues one TL-UL request per AXI beat; the single B response comes after the last one.

Good & bad practices

✓ Good practice

Start every debug with --trace on the failing address; open waves only at the hop where the trace stops or changes.

Why: the trace tells you in seconds which boundary is wrong; waves of the whole chip are slow to navigate.

✗ Common mistake

Comparing IDs across boundaries and calling it a bug when they differ.

Why it hurts: the ID grows at xbar_main by design ({host index, ID}); compare the low 4 bits.

✓ Good practice

Learn on axi_csr_reset (7 reads, CPU idle) before reading waves of a firmware test.

Why: firmware tests have ~20k transactions of instruction fetches around the one you want.

✗ Common mistake

Looking for an AXI burst at the IP's TL-UL port.

Why it hurts: bursts end at the device bridge; on TL-UL you will see one request per beat.

Activity — triage

A new test that reads spi_host0 registers hangs until the 20 ms timeout. The previous test in the same firmware gated clk_io_peri. Where do you look first, and what do you expect to see?

Which clock does spi_host0 use, and what does a device bridge do while waiting for a TL-UL response?
spi_host0 runs on clk_io_peri (96 MHz). With it gated, P.if_dev_spi_host0 shows the AR accepted by the bridge, then nothing: F.tl_spi_host0_o.a_valid high and no d_valid from the stopped IP. Ungate the clock before touching the IP (and clk_freq/fw_clk_gate show how to check it).

The scoreboard reports expected DECERR (unmapped) for a UVM read of 0x4006_0000, but the read returned OKAY. What is the most likely cause?

OKAY means some device accepted it. --trace 0x40060000 shows which dev.* port saw it; then compare that device's rule in titan_axi_fabric.sv with fabric_ports.json.

Good & bad practices

✓ Good practice

Read the first error, not the last.

Why: one wrong transaction usually produces a cascade; the first message is the cause, the rest is fallout.

✗ Common mistake

Raising timeouts to make a hanging test pass.

Why it hurts: a hang is a missing response somewhere — the bug is still there, only hidden.

✓ Good practice

Reproduce with the same seed before changing anything.

Why: if you cannot reproduce it, you cannot know you fixed it.

✗ Common mistake

Debugging the whole chip when a standalone bench exists.

Why it hurts: uvm/bridge_tb runs in seconds; a chip run takes a minute and boots for 2 ms before anything happens.
